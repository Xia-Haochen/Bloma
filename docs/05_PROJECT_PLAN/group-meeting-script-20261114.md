# Bloma 本月多 Agent 协作与验证机制进展

汇报日期为 2026 年 11 月 14 日。工作范围为 2026 年 10 月 14 日至 11 月 13 日，代码核对基线为 `686c0af`。按约 12–15 分钟准备，实际时长取决于语速和演示。加粗段名用于换页提示，正文可以直接口述。实现调用链、参数和证据出处见[技术核对说明](group-meeting-technical-reference-20261114.md)。

**一　本月做了哪些核心变化**

这一个月，Bloma 的工作集中在四个方面。第一，围绕贯穿需求与制作的主会话，完善持续执行、中断恢复和工程状态管理。第二，引入独立实验子 Agent，让系统面对未知能力时可以查资料、运行小实验，再依据结果集成。第三，完善独立审阅，以及绑定具体候选版本的验证和缺陷修复流程。第四，升级文件、进程和代码查询工具，减少重复读取与无效反馈。

十月中旬，我们还做了一套六组调度对照。每组运行一轮，使用十四个共同业务场景。两个直接实现基线都通过了十四项检查，混合调度在这套样本中没有超过最佳同质组。六组里，业务全通过的有四组，同时完成交付并通过业务检查的有三组。

这些观察推动我们进一步关注协作的信息质量和执行责任。后续工作主要围绕怎样探索未知能力、怎样把实验结果带回主工程，以及怎样核对生成结果展开。下面重点讲这些实现。

**二　同一主会话负责需求与制作，实验子 Agent 处理关键未知**

当前用户沿同一个 Bloma 主会话沟通需求、确认目标并进入制作。内部根据阶段调用不同处理逻辑，需求阶段进行结构化澄清和确认，确认后沿同一会话 ID 进入持续 Pi 制作流程。制作阶段默认由一个主负责人完成实现和集成。

为了扩展能力边界，本月重点增加了独立实验委派。主负责人遇到陌生格式、未知依赖或不确定的技术方法时，可以先描述要回答的问题和判定条件，让实验子 Agent 查资料、检查环境、编写探针并实际运行。例如，先验证现有环境能否完成视频拼接，再决定主工程怎样接入这项能力。

实现上，主负责人沿既有委派工具提交 experiment 参数，其中包含实验判定条件和需要复制的输入文件。宿主创建独立子会话与实验目录，登记父子关系并配置实验工具。子 Agent 使用自己的模型与工具循环，可以持续调查、运行和修正探针。

Pi 负责循环、会话持久化和上下文压缩，Bloma 负责工作区、工具权限、预算和证据。实验子任务继承父级执行约束；当前委派机制最多两个并行子会话，深度限制为一层。

普通代码分工委派也有工具支持，其使用条件是工作独立且值得并行。本次汇报重点是通过实验解决关键未知，正式产品的实现和集成责任仍由主负责人承担。

**三　实验怎样运行，结果怎样进入正式产品**

实验工作区位于工程之外。宿主只复制指定输入，文件工具指向这个实验目录，命令也在对应目录和数据环境中运行。每次命令保存命令参数、运行前源码指纹、退出码和输出。当前单次实验命令最多六十秒，取消会传递给执行器。

子 Agent 通过 record_experiment_result 提交方法、发现、判断和产物。判断可以是支持、反驳或仍未解决。平台要求支持和反驳结论已有实际命令运行记录，同时把判断保留为 Agent 的解释，供主负责人进一步核对。

实验产物被复制到证据目录并记录哈希。后续继续修改或运行，会让当前结论指针失效，同时保留已封存的历史材料。主负责人通过 read_experiment 读取运行事实和代码产物，判断是否适用，再用正常文件工具集成到正式工程并重新验证。主工程版本变化时，也会提示重新核对适用性。

平台组件因此成为可选资源。组件契约合适时直接复用，缺少现成能力时，可以通过资料调查和最小实验寻找方案，再集成验证。目录隔离负责组织实验和控制普通文件工作，命令仍在当前用户权限下运行。

历史视频实验中，真实子 Agent 找到了 imageio_ffmpeg，写探针、修正路径并生成了视频产物。停止后独立检查确认了红蓝片段和非静音音轨，但该轮达到测试轮数限制，尚未提交正式实验结论。这个结果说明探索确实产生了可检查的产物，也暴露了限额前交接的问题。后续加入了未完成产物封存，让主负责人能继续核查已有工作。

**四　开发协作之后，怎样组织独立质量审阅**

主 Agent 集成出候选后，宿主安排必要的质量审阅。代码审阅者 C 检查逻辑、数据和工程实现，视觉审阅者 V 检查实际界面。平台还支持可选的独立案例设计 B，从确认需求出发形成验收场景。

C 和 V 也沿现有委派机制创建子会话，但它们的任务材料与权限单独配置。代码审阅者获得确认目标、候选资料和只读代码工具。视觉审阅者获得宿主采集的实际图片以及相关观察事实。当前自动 C/V 使用父级渠道，独立性主要来自任务、上下文和权限边界。

这里还有一个重要问题，就是不同角色可能看到不同版本。制作方改完代码后，旧截图、旧审阅结论和旧测试结果的适用性都需要重新判断。

为此，平台把源码与依赖摘要、确认目标和运行环境关联为候选身份。审阅和验证记录携带这个身份。视觉图片来自实际运行实例，并有图片哈希和材料清单。到收尾时，宿主检查证据是否对应当前候选。

协作安排也参考已发布基线和当前差异。逻辑、数据、依赖及未知变化保留完整审阅；符合严格条件的小范围纯样式修改可以聚焦视觉审阅；输入和有效基线一致时，可以复用适用证据。这让审阅力度和实际风险关联起来。

**五　审阅发现的问题，怎样真正关闭**

审阅者提出问题时，需要给出需求依据、触发条件、位置、证据和复现建议。宿主把它们记录到工程外的质量台账中，并保留疑点、争议、已复现问题等状态。

对于需要动态验证的问题，平台把问题与具体案例关联，再实际运行。一个受控回归案例展示了这种协作的作用。制作方的自测只检查对象 A 能否保存，独立案例进一步修改 A，再检查对象 B，发现 B 的数据受到污染。修复实现后，平台重新运行原来的冻结案例，并同时保留修复前失败和修复后通过的结果。

关闭这类缺陷需要核对原失败依据、案例绑定、修复候选和当前执行结果。测试程序真实启动，案例真正执行，结果才能进入结算。环境或定位失败则保留为未验证状态，继续调查。

交付责任也在本月进一步收敛到宿主。制作方形成稳定候选并完成登记检查后，宿主组织必要审阅、问题结算和发布。发布前再次核对候选，随后把活动版本和对应项目生命周期一起更新。这减少了制作 Agent 在收尾阶段需要自行串联的内部操作。

**六　测试本身出错时，怎样修订**

最近的课题资料工作台暴露了一个典型情况。测试把第二段正文里的文字改成了纠正后的内容，读回断言却检查第一段标题。当时数据库中的正文已经保存成功，错误出在测试定位。

平台为这种情况提供了正式修订流程。先封存修改前后的测试和依赖输入，在隔离候选中执行拟议修订，再把确认需求、原测试、拟议修改和执行结果交给独立评审。修订批准后，宿主应用对应版本，并重新执行正式验收。

同一个项目还暴露了真实产品缺陷。任务取消后重试沿用了旧取消状态，导致等待无法结束；后台刷新还可能在点击保存前重建编辑框，覆盖正在编辑的文字。这些问题分别通过任务状态修复和编辑界面状态保护解决，再通过实际用例复验。

最近一批平台改动补齐了失败证据的传递。安全探针现在保留命中文件、行号、类别和候选身份。执行超时会保留正在运行的案例及最后操作状态。修复方因此可以沿着具体现场继续调查。

**七　工程伙伴与工具升级的结果**

本月还实现并试验了持续工程伙伴。它接收制作过程中的公开行动和实际工具结果，在自己的工作区与会话里继续调查，有新事实时续接同一个伙伴。它可以提前交接发现，也可以继续使用工具核查。

真实试验同时暴露了额外调查消耗请求、延长收尾的问题。因此工程伙伴保留为可选能力。主流程进入正式收尾时，宿主优先处理必要审阅和发布，业务问题返回制作后再继续相应调查。

工具方面，本月补充了批量读取与编辑、文件版本校验、进程管理、增量日志、TS 和 Python 语义查询，以及 DOM 和 Windows UIA 观察能力。

其中，文件编辑在应用前核对读取时的内容版本，发生变化时要求重新读取。日志使用游标返回新增内容，历史内容仍可查询。语义查询则帮助 Agent 查找定义、引用和诊断，减少反复通读文件的需要。

我们对固定工作流做了受控对照。文件工具调用从五次降到三次，总工具调用从十三次降到十一次。两个样本合计的工具返回字节量约下降百分之七十，SDK 消息累计字节量约下降百分之五十一。两种调用形态的 SDK 轮数都保持十二轮。这组结果说明了重复返回量的改善，真实模型成本和自主完成效率还需要单独测量。

**八　当前完成情况与结项工作**

工程验证方面，工具升级在对应历史版本的标准离线回归中，通过了六十个文件、六百零五项检查，另组 Python 检查十七项通过。最近课题资料与组会工作台在修复后，通过了十七项本机正式验收，覆盖导入、OCR、音频转写、文字纠正、取消重试、导出、备份恢复和关闭重开。

这些结果分别对应平台机制和具体产品。最近工作台的修复包含外部工程介入，真实模型接口效果和跨机器安装仍需要各自验收。

结项阶段准备固定演示版本，整理本月的实现、失败现场与复验材料，并记录每次人工介入。后续对照会围绕单制作 Agent、加入代码审阅、加入代码与视觉审阅等配置，观察最终业务完成率、人工介入次数、总费用和交付耗时。
