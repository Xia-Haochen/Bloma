# 个性化开放需求生成：v5 架构与实施方案

日期：2026-11-04。核查代码基线：`5ed3ae1`。状态：设计已更新，以下新增协议尚未实现。承接[v4](complex-wish-generation-plan-20261101.md)、[已有实施](complex-wish-implementation-20261103.md)及[收尾改进](complex-delivery-closeout-20261104.md)；本版替代旧方案的复杂度定义、下一批优先顺序和测试选题，不撤销既有身份、费用、证据、数据和发布边界。

## 1 目标与判断

用户可以提出没有现成产品分类的个人愿望，包括特殊交互、私人例外、开放规则、混合素材、跨次纠正和中途改意。系统应保留这些决定产品价值的内容，选择合适的实现，并给出与实际证据一致的交付结果。页面多、功能多和分期多不单独构成复杂度。

11月3日两个样本重新定位为中等复杂度本地业务应用；它们证明了一些业务路径可用并暴露交付问题，未证明开放需求能力。11月4日收尾改进也不等于意图保真已解决。

原则：宿主维护有限、可验证的协议；生成应用实现开放的领域行为。默认继续使用一个制作/集成负责人、现有Pi执行器及有界委派。不得为“审判庭”“考古”“沙盘”等题材添加平台分支、关键词路由、固定界面或专用验收后门。

## 3 架构：同一事实源，三类责任

### 3.1 意图契约属于平台需求域

以PrdBackplane为唯一确认事实源，优先对RequirementsModel作兼容扩展；不新建一份与requirements/constraints竞争的“愿望数据库”。功能继续使用F编号，规则/场景引用它们，不复制功能正文。

拟议最小扩展（名称在实现时定稿）：

| 概念 | 必须表达 | 权威与行为 |
| --- | --- | --- |
| 用户来源 | 宿主创建的消息/材料引用、版本和原文片段；材料沿已有MaterialSourceRef | 模型只能引用真实来源，不能伪造用户说过的话。敏感原文按需读取，不复制进每个子任务。 |
| 核心体验 | 用户主要使用旅程、必须保留的特殊交互、明确不能接受的替代方案 | 只有用户表达或已确认决定能成为承诺；不能因使用模板而降为装饰。无需为所有简单任务填写复杂表单。 |
| 规则与例外 | 适用对象/状态、触发条件、结果、例外、来源、暂时或持续有效、替代关系 | 先保存可观察语义，不建立支持任意代码执行的规则DSL；冲突不能由模型默默选择。 |
| 正反场景 | 一个可接受过程与一个“看似完成但违背愿望”的过程，引用规则和F编号 | 用户无需编写测试。Agent起草，宿主校验引用；决定产品方向的歧义才询问用户。 |
| 判定依据 | 确定性不变量、来源证据、体验评价及未知项 | 字符串完整、引用有效只证明结构正确，不证明理解正确。允许多个实现满足同一愿望。 |

使用两个不同检查：一是宿主检查引用/覆盖/版本；二是对原始愿望与整理结果做语义核对。语义核对优先纳入已有整理/审阅上下文，不默认增加常驻模型角色。确认卡展示“最重要的体验、例外、尚未决定之处”，不要求普通用户阅读内部schema。

### 3.2 能力组合属于制作域，领域规则属于生成应用

从确认行为推导所需输入、处理、状态、交互、外部依赖和结果证据。选取已有组件或直接编写业务模块；组件目录不是产品类别白名单，不限制新交互和运行形态。

每个采用的组件记录：版本、实际接口、输入输出、错误/取消方式、数据目录、依赖与准备状态、对应F/规则引用和验证入口。实现与候选清单一同受版本保护。短程序不强制拆成多模块；跨状态/外部副作用/长任务才要求清楚的边界。

生成应用内建议分开：领域状态与规则、素材/数据适配、交互呈现、外部AI适配。示例是拆分方式，不是统一框架：小说规则、道具身份和叙事风格不得写入平台宿主。只有在至少两种无关需求中出现相同、稳定的机制缺口，才将最小机制提升为可复用组件。

能力预检要回答：本轮制作可用什么、交付后应用可用什么、仍需配置什么。明确要求的核心能力不可静默降级为示意；无法准备时保留可运行部分和阻塞原因。拟议能力组合记录复用component/runtime/capability绑定，不新建权限或费用系统。

### 3.3 产品运行数据属于产品域

严格区分：开发需求/决定；产品用户记录/偏好/纠正；模型推断和创作输出。三者有不同的版本、存储与授权范围。

复用现有store、jobs、media，并按需求补充最小数据约定：稳定对象ID、来源引用与源版本、结果类型（来源事实/推断/创作）、纠正版本与作用范围、关联派生结果。当来源或规则变化时，生成应用明确选择保持历史、标记过期、重算或产生新分支；不能悄悄重写过去。取消后的迟到结果、重复提交和过期纠正沿现有revision机制处理。

“忘掉这个”需要在该应用已确认范围内规定删除/失效行为：原记录、偏好、缓存及派生输出各如何处理。备份和导出副本的边界须说清；不承诺无法验证的全局擦除。不建设默认跨应用个人画像库或无限记忆，也不强制向量库、事件溯源或云服务。

## 4 验收与交付接线

建立可追溯链：原话/材料 → 已确认功能与体验/规则 → 实现模块/组件 → 场景及判定依据 → 当前候选的执行证据。关联视图从已有权威记录派生，不成为第二套状态机。

验收分维度报告，不以总分掩盖缺项：

1. 确定性行为：身份、例外优先级、状态变化、取消、恢复、数据迁移等，用宿主真实执行验证。
2. 来源与纠正：输出引用能回到当前素材；缺证据时保留未知；纠正/删除后派生内容按规则失效。既检查记录，也检查UI展示。
3. 体验忠实度：根据原话及正反场景观察真实旅程。按钮齐全、角色台词或四项视觉记录不能替代玩法成立；截图/录像/输入输出样本作为证据。
4. 开放输出：用可解释rubric和约束评价，避免冻结具体句子。模型评审是有依据的意见，不自签PASS；主观偏好无法由宿主确定时明确报告待用户评价，不伪造“完全符合”。

独立验收扩展采用版本化oracle集合：先加有限的集合/数值/状态关系、来源关联与变换前后不变量；开放输出评价分开记录。只允许宿主支持且校验过的判定器，不接受评审者任意生成脚本获得宿主权限。已有原生测试可验证复杂交互，但其预期仍必须追溯确认语义。

新增语义字段改变时必须影响需求哈希、scope、UX确认、阶段契约、独立设计及交付回执。首版采用保守失效并明确原因；定向复用属于后续优化，不能只改类型定义而漏掉消费者。旧项目按旧协议读取，不自动将推断内容补成用户承诺；续改时只确认实际新增/变更的语义。

## 5 实施顺序与完成条件

使用W编号避免与v4 P0–P6的已完成批次混淆。先完成一条端到端最小链，再扩展组件；各批实现需独立验证与提交。

| 批次 | 接线范围与依赖 | 完成条件 |
| --- | --- | --- |
| W0 意图不断链 | 需求模型兼容扩展、宿主来源引用、lean-brief解析、lean-scope差异/确认、production-context/working-context、C/V材料；引用RequirementsModel已有概念 | 普通请求不膨胀；特殊体验/例外不被删除；压缩恢复、委派、改意后仍读取当前版本；新语义使旧证据失效。 |
| W1 判定依据与独立测试 | 依赖W0；扩展有限oracle、场景矩阵与质量报告；接quality/verification/regression，而非旁路“体验通过” | 能检出“普通列表＋聊天框”替代特殊旅程；不能靠把所有句子原样复制进brief过关；错误oracle保留争议。用未见样本先做离线核对。 |
| W2 能力组合与纵向切片 | 依赖W0/W1；复用capability准备/组件契约，接运行时依赖和最小关键旅程验证 | 一条核心体验贯穿真实输入、领域规则、持久状态、交互及证据；缺产品运行凭据能真实呈现待配置，不能被开发环境成功掩盖。 |
| W3 产品纠正与变化 | 依赖W2；以store/jobs/media/data-update为基础补跨结果来源、规则版本和失效接口；仅抽取跨题材共性 | 重命名、例外、纠正、中断、撤回/删除及升级在至少两种不同领域有受控回归，旧数据和原始素材不被误改。 |
| W4 有边界的真实复验 | 依赖上述相关批次，使用配套测试计划与新的明确费用范围 | 多类愿望的初次生成、使用中变化及恢复均留证；分别报告功能、体验、正式交付、人工介入及费用，不以样本个数推算可靠性。 |

W0/W1是最高优先级。若意图已在整理时丢失，增加多模态工具或更多Agent只会更快完成错误产品。W2/W3的通用机制随缺口实现，不能先建完整万能应用运行时。

## 6 确定做与需要验证

确定做：来源和承诺可追溯；保留特殊体验与例外；同一事实源及版本失效；区分开发状态和产品记忆；真实核心旅程；分维度证据；按行为组合能力；覆盖变化和恢复的跨题材测试。

待验证：何时自动展开结构模型、最小需要多少字段/上下文、开放体验rubric的一致性、哪些纠正机制值得组件化、多状态视觉采样的收益，以及这些变化对真实完成率/用户重复解释次数的影响。每项先记录漏项或误判，再调整；不将自动语义核对声称为数学完备保证。

明确不做：题材路由表、万能规则DSL、默认知识图谱/向量库、全量重写工作流、把主观趣味简化成单个评分、默认递归Agent组织、为了新任务重置预算、重新启用已退役PRD长流程。
