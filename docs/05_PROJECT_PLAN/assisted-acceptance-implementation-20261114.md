# 统一实测入口：设备采集与 ASR 首批实施

日期：2026-11-14。对应 [场景与扩展设计](assisted-acceptance-design-20261114.md)。本批补全平台入口与证据恢复链，不将当前语伴项目标为完整交付。

## 实现范围与职责

- `main/software/assisted-acceptance.ts` 管理项目、操作、确认范围、候选和尝试身份；复用现有运行注册表、取消信号和原子文件写入。每次尝试独立留档，重启后未完成尝试投影为 interrupted。
- `main/software/microphone-acceptance.ts` 负责设备采集与 ASR 观察、可人工核对的条件及证据保存。会话不增加一个制作/评审 Agent；新增领域检查继续沿适配器边界实现。
- `main/desktop/speech-verification.ts` 仍是语音证据的读取方。正常自动验收不会自行开启麦克风；只有实测入口的明确录音操作才触发设备录音。
- `main/software/verification.ts` 保持正式验收权威。缺实体采集时仍执行独立 B，B 适配未齐也不再遮蔽正常启动检查。补证改变 verificationInputs，不复用缺证据的旧报告。
- `main/desktop/lean-production.ts` 对当前候选的麦克风待办进入 waiting_user；“继续”不再为同一设备缺口调用制作模型。观察到的 B 产品失败仍走原修复流程。
- 发布仍经过 `deliveryQualityGate`、原里程碑或发布服务；前端与人工反馈没有直接写 completed 的权限。

一个既有项目 IPC 通道承载 query/start/capture/cancel/open/feedback。capture 是设备准备后的明确录音动作，open 固定待测候选，feedback 只能核对已存在的本次观察。没有增加面向制作 Agent 的内部验收工具或第二套发布状态机。

## 用户交互

在交付面板打开“继续验收”，准备设备，选择输入，点击“开始录音”。8 秒录音期间显示明显状态、倒计时与输入音量；设备真正打开后才显示录音开始。取消只终止本次拥有的执行。原始 PCM 留在内存，不落盘。

界面显示设备名、实际转写和音量观察。自动整句比对不一致时，只有固定音频检查通过、至少四次真实解码、有有效声音和非空转写的观察才允许人工核对。用户可以确认“转写符合我刚才说的内容”，也可以重新测试。人工核对保存独立 feedback.json，原 observations.json 的自动失败保持不变。

按钮采用明显主次样式、至少 44px 操作高度、独立操作区与焦点边框。验收状态变化会刷新主面板，避免局部结束后仍提示旧动作。

## 本机实际执行

项目：`9a419eea-12e2-45e3-8c8d-6c3fb20c0012`（AI角色语音聊天）。

实测候选：`3fc45b5285e674b883574235dc6876436b489bb488468d1b7d1d6884feee7193`。

1. 从正式报告读出 F-001 的 microphone 待办，GUI 已通过；实际启动 Bloma，从界面准备设备。
2. 用户选择 WH-1000XM5。第一次实际转写 `Jia3点6分。`，RMS 约 0.003179，自动比对失败，未产生通过证据。
3. 第二次实际转写 `嗯下周四下午3点开会。`，RMS 约 0.002593。固定三组输入均通过、真实解码四次，整句自动比对仍失败。
4. 用户明确表示此次可以通过。通过正式 feedback IPC 将人工核对绑定第二次 attempt `c2a79ccc-d9ed-4067-9a40-de1adbd7400d`。自动失败未被覆写。
5. 平台自动以同一候选调用正式复验：core 与 GUI passed，microphone 待办消除，B unverified。未越过 B/C/V/缺陷关闭或发布条件，项目未标为 delivered。

以上是两次真实设备采集，不是播放固定音频冒充说话；没有为此发起新的付费模型调用。用户认为声音偏小，但现有证据不能确认音量就是转写差异的唯一根因。

## 当前边界与剩余项

本适配器的实际观察范围为声卡设备采集和候选声明的 Python ASR callable；它不代表成品 MediaRecorder 按住/松开链路、语音播放听感或模型回复质量已经实测。已有 GUI 通过记录仍按其受控采集范围解释，不能拼接成“成品全链路实体语音通过”。成品窗口物理采集观察、播放与外部服务适配器属于后续实现。

首批结束时 B 的 F-002/F-003/F-004 缺 `INDEPENDENT_ADAPTER.json` 控件映射（`INDEPENDENT_ADAPTER_REQUIRED`）；F-001 已产生独立能力检查结果。随后已补齐映射并实际复验，新的环境前置条件和结果见 [B 控件映射复验](independent-control-mapping-20261114.md)。平台仍保留原 C/V 与缺陷关闭检查。

补充复验发现正常启动检查原先被 B 提前返回遮蔽：成品把静态标题“语伴 · 与角色语音对话”改为“语伴 · 与林知夏语音对话”，按固定标题查找产生了假阴性。平台探针现优先使用标题提示；不匹配时只允许本次启动进程树中唯一可见、非错误对话框窗口作为候选，继续执行响应、稳定和优雅关闭检查，并保存实际标题与是否匹配提示。不会从其他进程借用窗口。旧失败日志保留在 `run-artifacts/assisted-live/pinned-final-verification.log`，修复后的同候选复验见 `pinned-fixed-verification.log`。

最终同候选复验：core passed、GUI passed、正常启动 passed、B unverified；总结果仍 unverified。通过统一入口打开的独立试用也绑定同一 `3fc45b...` 候选，独立测试数据目录，不替换活动发布。没有新的实体录音要求或付费模型调用。

设备观察保留原候选、规则、操作、环境摘要与适配器版本；人工核对同时保存观察时和核对时的输入身份，要求候选源码、范围与冻结规则一致。最终运行环境重新执行自动检查。首批沿用既有语音证据时间窗口，尚未建立设备热插拔、操作系统输入增益变化的自动失效侦测，不能把昨日录音理解为今天所有设备状态已验证。
