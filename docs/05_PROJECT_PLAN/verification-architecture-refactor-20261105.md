# 测试、验收与交付职责收敛

基线：795327f。目标是降低 Agent 使用负担和重复解释，不增加新的审批或测试协议。

实施顺序：
1. 集中解释 GUI、CLI、B 案例证据；报告、诊断和缺陷闭合复用，执行器保留原始事实。
2. verify_app 与宿主收尾复用同一个精简回执。默认只返回状态、摘要、一次失败说明、有限案例、报告入口及下一步；完整报告仍可分页读取。
3. 通过后由已有宿主收尾机制推进审阅与交付，不再指引 Agent 为确认通过重复查询/验收。失败仍沿原案例修复；长期确认与发布守卫不变。
4. 用真实失败→反馈→修复→通过→交付的可控 Agent 回归验证，并保留前两轮误通过反例。检查分类一致性、报告绑定与缓存失效。

职责边界：执行器负责观察，证据解释模块负责案例含义，诊断负责下一步建议，回执负责有界呈现，质量台账负责缺陷历史，宿主编排负责收尾，发布存储负责版本与持久化。不得让报告文字签发交付。

不新增通用状态机、不让 Agent 承担进程内版本管理，不把历史协议直接删除破坏已有项目。逐案例流式反馈需要执行器到工具运行时的明确通路，本次不以普通日志或新轮询工具冒充已实现的流式反馈。

## 已实施

- `verification-evidence.ts` 只依赖类型，集中 GUI 案例证据选择、CLI 实际退出结果、B 案例结果与失败定位。报告和质量收尾不再分别找同名测试的第一个事件；优先选择实际失败阶段，避免首次通过遮住重开失败。
- B 运行异常在诊断、工具结构化反馈和台账中保持一致。存在更早的适配器失败时，不借用它的 expected/actual 解释后来的产品失败。
- `verificationResponse` 统一 verify_app、审阅后的宿主检查、最终交付失败反馈。默认只呈现最多4条案例、一份失败说明和一个下一步动作；原始回执、报告哈希、分页和失效校验不变。
- verify_app 删除失败步骤、GUI/CLI/B案例和完整 evidence 的重复拼接。当前检查通过后提示结束制作，由已有宿主编排完成必要审阅；不让 Agent 为获得许可重复查询或验证。
- 新项目按需上下文默认展示原生测试路径，已有动作表项目仍获得动作表 schema 与示例。工具自身 schema 继续兼容旧调用。
- 当前源码绑定、已确认需求、冻结预期、缺陷复测、费用边界及长期项目显式确认均保留。没有增加新的审批流程或 Agent 工具。
