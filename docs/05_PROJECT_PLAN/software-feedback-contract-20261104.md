# 软件生成事实、诊断与反馈契约修复

日期：2026-11-04。承接`6f0406d`的收敛修复。用户要求修复三项：事实与诊断分离、关键上下文不被截掉、验证反馈能否引导正确的下一步。本批只改平台和受控测试，不新增真实模型调用、不修改涂鸦产物、不更改原费用/正式交付结论。

## 1. 同一观察事实与明确的判断边界

`verification-diagnostics.ts`不再用总体`failed`兜底推断产品断言失败。未知原因保持unknown；实际断言、宿主运行异常、适配契约和静态规则分开记录。静态安全规则命中为security_policy，不直接宣称漏洞可利用。CLI回执增加原冻结stdout/exit_code预期，不能只留下actual让模型猜预期。

失败输出保留兼容的category/code/expected/actual，同时明确提供：

- `observation`：实际状态、候选/源码、预期和实际值。
- `diagnosis`：判断依据、supported/suspected/unknown与`root_cause_confirmed:false`。断言失败只确认不符合登记预期，不自动证明业务实现根因。
- `input_identity`：宿主记录源码、需求范围、规则/夹具、运行环境的hash，以及request/operation归属；不暴露环境变量值。
- 指纹同时注明协议；工作区指纹与候选runtime inventory不跨算法直接比较。历史记录仍明确未重验，不仅凭hash字段存在就声称有效。
- `missing_evidence`：未记录输入身份、缺少断言预期、业务根因尚未确认等缺口。旧记录没有身份时保留未知，不补造历史证据。
- `next_action`：可调用的工具名和参数。未知先读diagnostics，断言先核对features，环境先inspect_software_environment，静态规则可定位到read_file；不再让模型解析带括号的伪工具名或猜runtime参数。

现役verify_app的即时反馈与`read_production_context(diagnostics)`共用`verification-report.ts`投影。共享ToolFeedback的assessment和恢复策略阻止“根因未确认但直接repair_product”的自动分类覆盖；仍允许模型在读清实际证据后正常修复。前置拒绝标not_run，已开始但未完成标failed，取消标cancelled，不能把所有异常都声称没执行过。

额度反馈新增准入状态，分别显示上限到达、请求预留不足、等待预留结算或原因未明的“额度保护未放行”。未知旧记录不再统称用尽；持久金额上限仍停止后续调用，不因文案修复而重置或绕过。

## 2. 最小信息集与可恢复的细节

恢复摘要保留项目/operation/当前源码、执行/验收/交付状态、当前阻塞、历史失败归属、未完成进程及数量、预算、最近验收的首个失败/未执行案例及预期/实际摘要、缺失证据和读取入口。

大体积意图与历史工具记录作为完整字段省略，`omitted_sections`明确列出原因及对应topic。长错误保留头尾并标注中段省略；脱敏原文留在宿主run-state，通过working-state可读。最小字段超过契约时明确报完整性问题，不截断JSON。Pi入口移除机械`.slice(0,8000)`：超限生产者明确显示摘要不可用，不冒充完整上下文。正常软件摘要经测试始终保持可解析且小于8000字符。

新`verification-report`主题沿已有只读上下文工具提供GUI、CLI、独立案例的统一页面：

1. 失败优先，其次未执行/未验证，最后通过；不再仅取CLI前6例或仅聚合GUI。
2. 返回完整计数、当前页数量、省略数量和下一页调用参数。
3. 长值显式标为preview/truncated，完整宿主记录可用`section=raw`分页取回。原始片段是带编码说明的字符串，不伪装成完整JSON对象。
4. 后续页必须携带第一页的`report_hash`；报告更新或hash不符拒绝混读。只能读当前项目的验收回执，不开放任意文件路径。
5. 所有事后读取都标`historical_not_revalidated`和`usable_for_delivery:false`。历史通过需重新核对，不能从查询接口取得新交付资格。
6. 验收尚未开始的错误明确`report_available:false`，不把旧报告路径当成本次失败证据。

CLI原始捕获输出在回执保留，不在执行层再做8192/4000字符的二次静默截断；模型侧投影负责限制大小，详情读取继续脱敏。执行器本身的进程输出/时间限制仍保持，本批不宣称无限保留任意进程输出。

## 3. 验证的是反馈链与动作，而非只检查字段存在

新增受控场景覆盖：

| 场景 | 必须观察到的行为 |
| --- | --- |
| 只有笼统失败，没有明确原因 | unknown；下一步读取诊断，不直接修产品 |
| 实际值不符合断言、预期来源待核对 | 保留expected/actual；先读确认需求，不宣称根因确认 |
| 独立预期有争议 | 读取独立设计，保留争议，不改产品迎合错误预期 |
| 环境阻塞 | 先调用真实存在且参数完整的环境检查入口，不猜runtime |
| 静态DOM规则命中 | 明确规则命中事实，不等同漏洞已复现 |
| 第29个CLI案例失败，前面通过 | 失败出现在首屏，未执行GUI案例仍可见 |
| 超长证据／报告更新 | 能按同一hash恢复尾部证据；更新后拒绝拼接旧页 |
| 超过十万字符的意图和历史 | 阻塞、进程、预算和验收摘要保留，JSON完整、略去内容有入口 |
| 原2400字符之后才出现关键错误 | 宿主原文和恢复摘要尾部均能找到，不在保存时丢失 |
| 预算尚有余款但预留不足 | 不显示“已用尽”，持久上限继续有效 |

实际Pi会话测试把同一反馈包送入下一轮受控决策，再核对执行的是diagnostics/features/环境检查而非write_file。它证明结构化事实、动作参数和恢复策略经过真实会话链没有丢失或被旧策略覆盖；不等于证明真实模型永远遵守正确反馈。

验证记录：联合8文件60项通过，包含实际CLI验证/复用/发布链、独立案例的真实浏览器失败与复测、Pi反馈传递、恢复摘要与UI标签。最后追加输入身份、长错误完整保留和恢复首屏晚序失败案例的3文件16项回归通过，与前组有重叠，不相加为独立样本数。类型检查、完整构建与文档检查通过。首轮旧标签断言仍期待“额度已用尽”，按新的中性/具体准入语义修订后通过，没有放宽金额保护。

## 边界与维护

提交前按源码不变量审查发现并修复一项额外问题：验证复用会在返回对象附加`reused`标记，不能拿附加后的对象hash当作持久报告身份。即时反馈现读取并核对宿主原回执；仅允许既有复用标记差异，分页始终引用原持久hash。实际验证工具回归增加“第二次复用后仍能按所给hash读取同一报告”的检查。此问题由源码关系推导后用测试验证，不等到真实模型试验发现。

后续工程顺序应保持：先列出事实来源、版本关系、缺失状态、控制权和合法下一动作的不变量，沿完整调用链核查源码；再对可能破坏这些不变量的路径做受控验证。测试通过说明所测路径成立，不能反推全部设计正确；真实模型试验只承担模型与开放任务行为的验收，不承担基础协议和状态错误的首次排查。

不建立另一套通过状态。质量台账、原宿主验收凭据及发布门继续拥有各自的事实；报告查询是投影，不签发PASS。候选、规则、环境变化仍使原复用条件失效。新诊断不能凭测试失败自行修改冻结业务预期，任何语义争议继续保留。

本批没有增加费用，没有把原575次请求样例标成成功。后续真实生成效果、跨模型遵从性和复杂体验质量仍是独立验收范围；本批结果用于确认信息契约和控制链修复，不以离线测试数量代替真实产品可靠性。
