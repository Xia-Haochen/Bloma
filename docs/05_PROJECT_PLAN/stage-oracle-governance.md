# 阶段验收反馈与冻结预期治理

承接109次物理请求复测暴露的问题。本批先离线修复通用平台机制，再沿原项目、原金额账本续验，不为具体应用设置例外。

## 通用控制关系

- 阶段验收复用完整验收的事实/诊断投影与ToolFeedback，明确partial_cumulative_gui作用域；有attempt和contract身份，可按宿主报告hash读取详情，不把局部检查当交付。
- 父测试取消、跳过或未完成标unverified；没有结构化失败断言的执行错误保留unresolved。实际交互失败或第一条断言失败也算执行过，不因成功断言计数为零而放松冻结保护。
- 重复失败按宿主结构化拒因和稳定证据指纹识别，适用于任意验收入口，不依赖工具名称白名单。同一工具同类契约拒绝/相同失败证据三次未解决即停。换文件、无关写入不清除阻塞；不同业务断言仍可区分。
- 观察员在传输前明确拒绝的请求使用类型化ModelRequestRefusal。保留尝试计数，仅释放此笔未发送输出预留；已开始传输、未知错误和取消的预留不释放，金额账本不由此改写。

## 冻结测试的争议与裁定

1. 制作方用read_test_contract读取宿主冻结原文或当前提案；长文件分页，不能读取任意路径。
2. propose_test_correction基于冻结原文提出唯一匹配的精确修改，绑定需求F编号和原scope。只解析新测试契约，不运行、不写回产品。保留原case名称、功能覆盖、输入文件集合及重开要求。
3. pending提案使父模型停止继续调用并阻止发布。制作方没有审批工具，不能通过附加reviewer字段自行批准。
4. 宿主decideTestCorrection必须提供独立操作者裁定、与已确认需求一致的预期来源以及可核对hash的证据。记录原/新测试契约和文件hash、裁定理由；来源范围变化或证据变化失效。
5. 批准后apply_test_correction仅应用该份精确内容，要求工作文件仍是原字节或已批准字节；其它文件干预、路径逃逸和符号链接拒绝。批准但未应用也不能发布。
6. 阶段检查、正式登记和旧行为保留共用同一精确修订检查。其它断言、入口组合、依赖及重开保护继续有效；原冻结档案和原失败记录不修改。
7. 重新实际运行累计案例，取得新候选结果后才能沿原C/V、里程碑确认及发布链继续。批准只许可测试修订，永不签发产品PASS。裁定版本参与验证缓存键，防止复用旧资格。

宿主裁定接口是正常工具层中的信任边界，并非宣称在同一操作系统用户下提供额外的进程安全隔离。后续若扩展为远程自动评审，仍须明确独立评审身份和证据来源；本批不让制作模型兼任批准者。

## 验证

离线验证覆盖：错误冻结预期在真实浏览器先失败；提案不能自批准；独立裁定后精确应用；原失败和原档案保留；修订后再次运行才通过。另含证据篡改、工作文件干预、范围变化、案例删除、跨项目/路径、未审批与批准未应用的发布阻止，以及未知工具名的重复拒绝停止。

联合回归7文件68项通过（包括实际阶段GUI、C流程、Pi运行与预算），随后裁定/验证链相关4文件35项通过；两组重叠，不相加为独立样本。新增发布与范围守卫的裁定测试6项通过。构建、类型和文档检查以本批最终检查为准。第一次真实浏览器纠正测试暴露“失败第一条断言但成功计数为零”的冻结缺口，已按真实执行证据修复再通过。

真实续跑必须继续逐请求记录，并把宿主裁定、人工恢复和平台版本变化单列，不能算作原基线一次自主成功；费用继续沿现有10元总窗口，不清零用量。
