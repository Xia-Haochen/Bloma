# 平台验收反馈与测试修订闭环

日期为 2026-11-14，工程基线为 `fad3345`。本批处理语音输入法演示暴露的平台验收问题，生产改动集中在三个现有模块。

**职责与数据流**

- `test-corrections.ts` 保留原冻结字节及应用路径，为评审生成可读投影。二进制输入提供路径、大小、哈希与 `content_available=false`，避免 Base64 占满文本输入。含 NUL 的 UTF-8 可解码数据同样按二进制处理。
- `test-correction-review.ts` 在启动隔离探针前校验固有文本材料大小，执行后继续校验完整包。独立裁定仍核对原预期、精确提案和实际执行。文件身份不能证明内容语义，无法依据当前证据判断时需要明确指出缺口。
- `verification-report.ts` 使用既有 `qualityWorkQueue`，在带验证输入身份的回执中返回对应候选的质量待办。包含执行失败和重要覆盖缺口，最多展示四项，长字段带原 finding 的读取入口。读取只投影已有记录，问题关闭仍由原结算流程处理。

质量台账继续保存问题事实，正式回执继续保存执行事实，测试修订档案继续保存封存输入和裁定。待办由这些记录派生。

**闭环验证内容**

真实浏览器回归执行原错误断言并保存失败，然后提交带 300KB 二进制夹具的完整修订。第一次独立评审返回无效结果，原提案保持 pending；再次评审批准后，工作区冲突仍被拒绝，恢复为允许的字节后由正常 verify_app 入口应用并执行。最后保留原 failed 和新 passed 两次阶段结果。

另有反例检查二进制封存与读回的哈希、超大文本在探针前拒绝、失败回执携带覆盖缺口、读取反馈不会关闭疑点、已闭合问题在候选变化后重新出现，以及长质量字段指向正确的 finding 记录。

完整回归发现既有额度测试先耗尽默认 4096 硬上限，又要求上限继续增加。夹具改为显式 16 次项目额度，继续检验已准入窗口补足额度和旧消耗保留。平台容量与生产预算规则沿原实现执行。

流式工具对照夹具原先只在后续 read_process 中识别 BUILD_READY，首次 run_command 已返回该信号时会随 next_seq 被消费，后续增量读取不再返回。夹具补齐首次命令返回的就绪观察，轮数上限、固定输入、构建启动次数及业务断言保持原要求。首轮工具组的 turn_limit 失败、诊断复跑及最终整组结果均保留。
