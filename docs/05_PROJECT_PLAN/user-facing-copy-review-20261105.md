# 用户可见文案审查与优化

日期：2026-11-05。范围：当前 software-v1 制作流程及共用交互组件。本批仅修改显示字符串及对应测试断言，不改变状态定义、流程、权限、验收标准或样式。

## 审查范围与取舍

- 需求确认：核对 ScopeConfirmationPanel、lean-scope/lean-guide 的确认及采纳行为；说明核对对象与确认影响，保留建议采纳后再次确认的原有说明。
- 界面确认：核对 ux-confirm 的草图就绪条件和确认选项 ID；明确草图确认的是外观，之后才制作功能。旧 RequirementConfirmDialog/PrdConfirmDialog 不做全量重写。
- 等待与制作：核对 WaitingFeedback、ChatPanel 的计时、重试事件、进度入口，MvpStatusBanner 的运行/暂停分支，以及 project-progress 的执行记录来源。
- 测试验证：核对 state-view 的历史检查与交付分离、trial 的检查来源、project-stages 的阶段检查；保留局部检查与整体交付的区别。
- 异常与恢复：核对交付面板的启动/读取回执、停止请求、长期维护操作异常；检查点选修改、消息发送和版本恢复的提示，保留其已有明确指引。
- 按钮与弹窗：权限允许/拒绝、草图确认、停止制作、查看进度、恢复备份。只修改存在明确理解或真实性问题的表达。

## 主要修改

| 位置 | 修改前 | 修改后与原因 |
| --- | --- | --- |
| WaitingFeedback | 超过120秒后只说等待较长 | 保留“当前任务”，说明等待时长不代表完成进度，不提供虚构百分比或预计时间 |
| ChatPanel | 网络不稳…你的消息不会丢 | 请求暂未成功，正在自动重试…暂时无需重复发送；事件只有次数，没有具体原因及消息持久化证明 |
| ScopeConfirmationPanel | 核对下面的内容 | 明确核对功能、限制、范围外内容，确认后按此范围准备界面或制作 |
| ux-confirm | 草图画好了…确认后我就开工 | 第N版草图可预览，核对布局外观，说明功能尚未完成；按钮为“确认草图，开始制作” |
| MvpStatusBanner | 完整功能已交付 | 当前版本已交付，引导查看交付说明中的检查范围与限制 |

| DeliveryPanel | 启动失败（通信异常） | 未收到启动结果，先检查是否已打开，避免直接重试造成重复启动 |
| DeliveryPanel | 项目还没有可展示的交付内容 | 暂未读取到交付内容，可刷新；读取失败不能证明不存在产物 |

## 仍存在的信息与体验缺口

1. DeliveryPanel.refresh 将错误响应/异常折叠为无数据，未保留具体原因。本批使用“暂未读取到”避免误判；要区分读取失败、尚无产物，需要后续补充独立显示状态。
2. retrying 只有 attempt/max_retries，不能区分限流、网络、服务故障。保留通用真实描述；不能承诺恢复时间。最大次数的边界含义也需结合重试策略另行规范。
3. ProjectExecutionPanel.cancel 未检查返回的 ok，API 缺失时可选调用也会继续执行。已去掉“正在保留现场”，但要确认停止请求是否被接收需要单独修复处理逻辑。
4. 部分 desktop_blocked.note、验证失败详情直接来自底层错误或模型文字，仍可能包含错误码、路径及内部术语。需要结构化原因和可执行恢复动作后再提供更精确提示，不能凭文案推断系统能够自行恢复。
5. 部分界面兜底依赖阶段字段，缺少运行事实时无法进一步区分暂停/中断/仍在执行；本批将交付空态的“正在接通完整功能”降为“当前处于程序制作阶段”，不修改状态归约。
6. 模型动态生成的需求摘要、说明与回复未逐条验证；本次保证范围为修改过的静态反馈和对应接线。

原有及期间出现的其他工作区修改均未纳入本批提交，不修改 Proma、记忆副本或生产流程文档；不推送远端。
