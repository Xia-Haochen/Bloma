# 复杂任务许愿式生成的能力核查与实施方案

日期：2026-11-01（Asia/Shanghai）。版本：v4。现役源码基线 `09a39e6529a28fffb7200d008a0fcb238b83eea1`，原方案提交 `efed31f`，v3提交 `f447e55`。本版沿用P0–P6编号，将P4改为可选优化支线，并补充委派收益、实际策略与执行透明要求；替代此前各版相关安排。当前仅修订方案，不启动运行时改造或付费生成。

目标：用户描述整体愿望，系统保留完整目标，自主完成已授权工作，并能在修改、中断和升级后继续交付可靠应用。普通用户不负责写完整技术规格和测试脚本。

决策：直接采用有实践依据的结构化交接、证据引用及有边界的独立调研/排障委派，补齐项目事实和真实验收。默认保留当前制作/集成负责人，不预设强制双层、负责人禁止工程操作或递归Agent公司结构。负责人需要理解产品与关键实现，必要时查证或完成小改动。只有出现可定位的持续问题，才开展对应优化比较，不以统一多轮A/B作为工程前置。

## 1 依据及适用范围

### 1.1 本仓库依据

现役链为 `agent-dispatch → handleLeanGuide → 短任务单确认 → UX确认或明确跳过 → runLeanProduction/Pi → 委派与工程工具 → C/V与宿主验证/修复 → quick发布或longterm阶段确认`。

核查依据是现役调用链、[质量交接](session-handoff-quality-20261030.md)顶部更新及[质量方案](multi-agent-generation-quality-plan-20261030.md)，不恢复旧 PRD/架构/裁判流程或已冻结实验。原始探查阶段的10文件/55项测试记录保留在第8节；本次代码复核是静态阅读，不把历史测试算作新方案已验证。

四处不能通过删除守卫解决的接线问题：

1. `collaboration-policy.ts` 的命令权限只给 `parentSessionId`；存在活跃writer时父端也不能运行。若禁用父会话工程工具并让普通child接手，将无人能集成验证。
2. `longterm-state.ts` 与 `longterm-control.ts` 校验session、scope、operation、revision和candidate。换执行者必须显式转交归属并使旧写入失效，不能把所有会话都视为合法负责人。
3. `withLeanRuntime` 持有操作级执行租约。不能给新协调者和制作执行者各套一层同租约，也不能另起operation躲开冲突或预算。
4. `quality.gate`、验证回执及发布前检查绑定当前候选和目标。任何新的任务/报告/事件协议都不能绕过这些检查。

## 3 确定实施与待验证选择

“确定实施”表示能力要求已明确，不表示文件拆分和所有实现细节已经定型；它们对单会话和分层结构都有效。

| ID | 确定要做的能力 | 原因与完成依据 |
| --- | --- | --- |
| D1 | 全部必需目标、当前范围、后续必需工作分开记录 | 不能为本阶段通过删掉未实现目标，也不能把承诺降为可选建议；阶段通过不等于整体完成。 |
| D2 | 任务独立于某次执行，交接关联产物、证据和失败 | 允许有依据地续跑/换执行者；报告不能单独改成verified，旧执行者迟到结果不能覆盖新状态。 |
| D3 | 关键约束直接提供，局部细节有索引可追查 | 已有近期摘要不足以代表有效决策；需有来源、适用范围、替代关系和当前版本。 |
| D4 | 跨模块业务旅程及累计回归 | 单模块通过不证明对象关系、状态流和历史数据正确；复用现有宿主与旧行为保护。 |
| D5 | 授权内推进、暂停、取消、预算和归属可恢复 | 不再让用户反复催继续；既有授权持续有效，范围/费用边界不能因自动化扩张。 |
| D6 | 记录真实结果与用户负担 | 同时测成品质量、恢复、干预、费用与时间，不能以并行吞吐替代质量。 |
| D7 | 分离推理、委派、并发和权限预算，并记录实际生效策略 | UI可综合展示，内部不能混成一个“更强”开关；比较结果时能分辨变化来源。 |
| D8 | 有边界的委派与简洁执行透明 | 独立调研等明确产出优先委派，小任务直接完成；用户能知道环境、当前工作、结果和取消入口，Agent数量不是质量指标。 |

| ID | 待验证选择 | 试验与否决条件 |
| --- | --- | --- |
| H1 | 委派粒度和触发条件的调优 | 有边界的独立调研/定位/审阅直接采用；只有出现重复探索、交接失真或费用过高时，才比较具体调整。 |
| H2 | 是否值得常驻一个独立项目协调会话，以及它应有哪些工程工具 | 当前暂不增加；持续协调拥塞、目标遗忘或前台阻塞被实际记录后才试验。已有委派收益不自动证明H2，负责人仍可查证实现。 |
| H3 | 摘要长度、自动读取与续跑节奏的调优 | 结构化交接和证据引用已列为确定能力；漏读、过度检索、串任务等实际问题才触发参数优化，不重新论证整个方法。 |
| H4 | 模型看门狗是否能发现现有重复失败机制漏掉的停滞 | 当前暂缓；出现漏报才做只读诊断试验，记录误报与成本，不赋予改目标、权限、预算或宿主规则的能力。 |

暂不做：每个微小动作都新建Agent、无限递归、默认增加并发或异模型角色、轻量Router必然适合项目规划、跨设备常驻、投机实现未采纳功能。它们不应成为第一阶段依赖。

## 4 最小结构及接线原则

### 4.1 先实现项目事实，不先建完整管理平台

业务权威仍是PrdBackplane中的确认需求及来源，新增结构引用它；发布、质量、费用仍由既有存储负责。建议最初只给现有长期状态增加任务与执行引用，避免复制另一套需求或交付数据库。

| 记录 | 最少需要表达的内容 | 权威 |
| --- | --- | --- |
| 项目范围与计划 | 需求ID、版本/来源、当前阶段、未完成必需目标、依赖、重要业务规则与待澄清项 | Agent提出结构，宿主校验引用；业务承诺来自用户表达和确认。 |
| Task | 稳定id、范围引用、完成条件、依赖、状态、产物/证据引用 | 状态建议为ready/running/implemented/verified/blocked/cancelled/superseded；verified由适用的宿主证据决定。 |
| Assignment | task_id、attempt、执行session、角色/写范围、输入版本、预算引用、开始/结束与交接原因 | 一项任务可以多次执行；只有当前有效执行归属能提交状态转换。 |
| 交接与决策 | 完成内容、关键接口/数据决定、未验项、失败事实、下一步、源码/案例/报告引用及适用版本 | 自述与宿主事实分开；摘要不能签发PASS，引用不能绕过会话/图片/材料访问权限。 |

对象是存储字段的设计要求，不必各建独立服务。初期不要求每个项目生成全面对象图、完整模块规格或长PRD。高风险共享实体/接口出现时，才补对应契约；普通用户不必决定技术栈。

### 4.2 范围与证据

当前执行范围投影必须保留原F编号和预期来源，包含本阶段变化及受影响的旧行为；总目标中的其他需求仍保留。范围投影是宿主操作，Agent不能自行删验收项。初期涉及共享规则的变更采用保守证据失效，再讨论精细选测。

特别注意：`regression-baseline.ts` 仅保留仍在当前brief中且需求哈希未变的行为。若只把本阶段需求写入brief，删掉旧阶段需求，会使retained为空或漏项。P1必须先明确累计已交付契约与本阶段制作子集的关系：正式回归仍能读到全部未变更的已交付承诺，本轮制作可取子集；在这个接线通过测试前，不启用阶段投影。不能仅靠界面保留总目标，底层却删掉旧验收义务。

已有C/V按稳定候选和风险策略运行，不为每个微任务增设一轮全审。Task的局部检查通过只能解锁相关依赖；项目/阶段交付仍经过完整宿主门。已确认重要缺陷的历史不能因为任务换ID或新会话而消失。

### 4.3 上下文与权限

项目视图提供目标、当前有效决定、阶段状态、依赖和需要用户决定的事项；工作视图提供具体入口、必要源码、失败和任务证据。两种视图先复用 `read_production_context`，不必先变成两个常驻模型。

每份材料携带范围/计划/候选版本。必要约束直接注入；低频细节附摘要和可读引用。读取旧规则要标明已替代，缺依据保留未知；恢复不能仅取“最近12条”。负责人可查证关键实现，局部执行日志不默认整批回灌。

共享工作区仍由一个当前集成执行会话持有命令权限，普通子任务继续遵守现有边界。若H2实验独立协调者，应将现有完整制作单元放到受宿主控制的执行会话，而非直接给普通child放开命令或递归权限。

### 4.4 可恢复的推进

先有稳定Task/Assignment，再补用户修改、任务结束、验证失败、依赖就绪等持久事件。明确归属的事件由程序投递；未知归属才作语义判断。每次转换核对task、attempt、输入版本、取消状态和授权；重复事件去重，乱序和迟到结果不覆盖当前状态。

事件持久化不等于外部副作用恰好执行一次。崩溃恢复先核对实际产物和回执；结果未知的外部写入不得盲重试。暂停状态跨重启保留，普通通知不能解除暂停。

项目总费用边界约束所有阶段、协调、执行、审阅及重试。当前operation内换Assignment不改预算键；阶段创建新operation也须计入同一项目授权上限。B保持明确的独立授权范围。业务重排在已授权范围内无需反复询问；新增业务、增加费用边界或扩大外部副作用才需要新的明确决定。

### 4.5 委派收益与实际策略

内部独立记录四个维度；面向用户可以给简单预设，不新增四个必须理解的设置面板。

| 维度 | 内容 | 不能隐含改变 |
| --- | --- | --- |
| 推理配置 | 模型、角色、请求的思考强度及生效来源 | 调高思考不自动增加并发或放宽权限。 |
| 委派策略 | 用户明确要求、项目/技能规则、必需质量角色、模型自主选择及策略版本 | 自动委派不意味着所有微任务都要拆分，也不替代任务范围授权。 |
| 并发与资源 | 同时活跃任务上限、排队、父子执行关系 | 更多累计子任务不代表更多同时并发；延续当前最多两并发边界。 |
| 权限与费用 | 工具/文件范围、环境、总预算与独立B授权 | 新建会话不获得新额度；角色提示词不能代替宿主权限检查。 |

在现有委派入口记录简短理由、明确产出/完成条件、输入版本、范围及预算引用。判断是否能缩短等待或隔离大量局部探索，先检查有无同版本同目标的在途任务/可用结果；失效证据不能当作可复用成果。普通小修改直接完成，共享模型和集成由统一负责人承担。这个判断不需要额外模型评审或新增一轮用户确认；用户明确要求和必需C/V角色依其既有规则处理，不能借“收益不足”跳过必需质量门。

独立调研、代码定位、限定排障和专项审阅优先沿用已有委派工具；可独立写入的模块按当前路径权限执行。子任务需要实际运行时请求父端集成执行，不能因任务名为“测试”就突破普通child命令限制。

复用 `RuntimeObservation` 和 `EvaluationStrategy`，关联Task/Assignment记录：委派触发来源与理由、策略revision、配置请求值、运行时解析值、适配后实际请求的允许记录字段、实际派生/开始/结束事件及费用。无法观察供应商是否采纳参数时标未知，不把配置值当服务端回执；仅记录脱敏配置和摘要，不存密钥或整份敏感请求。策略中的声明标签与实际事件分别保留，不能把“允许派遣”当作“确实使用了子任务”。

### 4.6 运行中切换模式

默认新推理/委派配置在下一次新Assignment生效，在途任务保留起始策略快照，并向用户说明生效范围。若支持运行中显式调整，只在安全边界更新并记录前后revision及请求边界；不能追溯覆盖旧记录。

取消、权限撤销和预算收紧优先于快照：停止新派发，在下一工具/请求准入前执行收紧，按已有取消机制处理在途工作；不能以“旧模式仍有效”继续越界。并发上限调低后停止超额新派发，在途任务按既有授权收尾或显式取消，记录暂时超过新上限的状态；不能隐瞒仍活跃的任务。调高模式不能自行增加已授权金额或新增渠道。

单纯策略变化不自动使相同候选的业务证据失效，也不证明证据可复用；仍由现有目标、源码、环境及审阅规则判定。`evaluation-identity.ts` 已把parent profile变化标为不可比，应保留该语义：运行中切换策略按revision分段统计，不能把整段作为固定策略对照。

### 4.7 对用户说明实际执行

开始工程工作时，用一句话或紧凑状态说明实际环境（本机项目副本、指定远程环境等）及当前动作；环境改变时更新。不把界面叫“聊天”解释为没有文件/命令能力，也不把本机执行说成云端沙盒。

默认仅显示在讨论、制作、检查、受阻或可用成果；可展开查看子任务目标、理由、状态和结果，并提供取消入口。来源必须是宿主Task/Assignment及实际工具事件：已派发不是已执行，执行结束不是验证通过。健康运行的工具细节保持折叠，在可用结果、必要决定、受阻或重要环境变化时通知，不每轮重复说明环境。

## 6 日常验证与定向优化规则

必做的是机制正确性测试与真实成品验收；结构化交接、有界独立探索和证据引用直接实施，不再重新证明这些通用方法。下列指标首先用于日常交付和故障定位，只有触发P4后才用于对应策略比较。

| 维度 | 观察方式 | 决策作用 |
| --- | --- | --- |
| 质量 | 外部业务验收、跨模块错误、旧功能回归、数据保存/迁移、最终未闭合缺陷 | 质量优先；不能用更快但更差的成品换默认上线。 |
| 连续性 | 中断、压缩、执行者交接、用户改意后恢复；旧规则/旧结果误用 | 每个失败都保留原始证据，检查是否新增失效类型。 |
| 用户负担 | 主动改意、必要业务决策、重复解释、平台求救分别计数 | 少打扰应体现为少重复解释和求救，而非隐瞒失败。 |
| 上下文正确性 | 必要约束是否收到、交接缺项、漏读证据、无用重复读取 | 主上下文变短只是诊断指标，不单独算质量收益。 |
| 成本和延迟 | 规划/执行/审阅/重试全量费用、首次可用时间、最终耗时、后台交接成本 | 包含失败、耗尽预算和新增协调费用。 |
| 执行可追踪性 | 推理/委派/并发/权限预算分别记录，派遣理由、在途任务与实际执行事件可核对 | 不以更多子Agent、更高档位或更多工具调用当作成功指标。 |

常规验收：用受控故障检查归属、幂等、取消、模式切换、费用和证据关联；用真实生成产物检查业务、回归、重开和数据。原P0三类任务作为验收与问题样本库，不要求每项功能先跑完整三类对照矩阵。离线回放能验证记录和接线，不能代替真实模型或真实产品效果。

P4启动时先写清问题证据、单一改动、预期改善、成本边界、验收与回退条件。覆盖原失败场景及至少一个相邻未调优场景；若随机性明显或结果反复，再做独立重复。样本与重复数量按问题风险在运行前确定，不规定统一“四对+补测”门槛。计费前核对当次完整预算，不沿用旧实验授权。

采纳要求：全部宿主身份/权限/费用/数据不变量通过，原问题确有改善，未新增严重数据损坏、越权或错误完成，相邻场景没有重要退化，成本/延迟符合事先边界。仅在已观察有效的范围启用；扩大默认范围前补对应覆盖。结果混合保持原默认或缩小作用范围；单个成功案例和小样本均不推算稳定可靠性。
